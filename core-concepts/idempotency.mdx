---
title: Idempotency
description: Make step reports safe to retry without recording a step twice.
---

Networks fail, and retries happen. Threadify makes sure a retried report doesn't
record the same step twice.

## How duplicates are detected

Each report has an idempotency key. If Threadify has already recorded a report
with that key on the thread, it keeps the first one and treats the new one as a
duplicate.

By default the key is derived from the step name and its context. Two reports of
`validate_cart` with the same context are the same report.

## Choose the key yourself

When two genuinely different operations would have the same name and context,
or when you want retries of one operation to match even if the context changes,
set the key explicitly. A good key is an ID from the system that did the work:

<CodeGroup>
```javascript JavaScript
const charge = await payments.charges.create({ amount: 9999 });

await thread.step('charge_payment')
  .idempotencyKey(charge.id)
  .addContext({ amount: '99.99' })
  .success();
```
```go Go
charge, err := payments.Charges.Create(&payments.ChargeParams{Amount: 9999})
if err != nil {
    return err
}

_, err = thread.Step("charge_payment").
    IdempotencyKey(charge.ID).
    AddContext(map[string]any{"amount": "99.99"}).
    Success(ctx)
```
```python Python
charge = await payments.charges.create(amount=9999)

await (
    thread.step("charge_payment")
    .idempotency_key(charge.id)
    .add_context({"amount": "99.99"})
    .success()
)
```
</CodeGroup>

Never reuse a key for a different operation; the second one would be dropped.

## With permission grants

A step reported after [`waitFor`](/core-concepts/execution-waits) is tied to its
grant, so each permitted attempt is recorded separately even if the name and
context are the same.

## What this doesn't cover

Idempotency stops Threadify recording a step twice. It doesn't stop your code
from charging a card twice. Use your payment provider's or tool's own
idempotency key for the action itself.
