---
title: Record steps
description: Report each operation in a thread with its outcome and data.
---

A step is one thing that happened in a run: an order received, a payment
taken, a tool called. You report it with a name, an outcome and some context.

<CodeGroup>
```javascript JavaScript
const order = await receiveOrder();

await thread.step('order_received')
  .addContext({ orderId: order.id, total: order.total })
  .success();
```
```go Go
order, err := receiveOrder()
if err != nil {
    return err
}

_, err = thread.Step("order_received").
    AddContext(map[string]any{"orderId": order.ID, "total": order.Total}).
    Success(ctx)
if err != nil {
    return err
}
```
```python Python
order = await receive_order()

await thread.step("order_received").add_context(
    {"orderId": order.id, "total": order.total}
).success()
```
</CodeGroup>

You can create the step before doing the work and report it afterwards. The
step's duration is measured from when you created it:

```javascript
const step = thread.step('payment_taken');
const payment = await takePayment();
await step.addContext({ paymentId: payment.id }).success();
```

## Outcomes

| Method | Use when |
| --- | --- |
| `.success(message?)` | The operation worked |
| `.failed(message?)` | The operation ran and failed, for example a declined card |
| `.error(message?)` | Something went wrong unexpectedly, for example an exception |

The optional argument is a message string or an object of details. Put data you
want rules and metrics to use in `addContext` rather than in the message.

Each of these returns once the step is recorded. To wait for the contract's
verdict too, pass `{ waitFor: true }`. See
[Check before acting](/core-concepts/execution-waits#after-reporting-the-outcome).

## Context

`addContext` attaches key–value data to the step. Values are stored as strings.
[Contracts](/core-concepts/creating-contracts) check context fields, and
[entity profile](/core-concepts/entity-profiles) metrics are built from them.
You can call `addContext` more than once before reporting.

## Retries

If you report the same step name with the same context twice, Threadify keeps
the first and treats the second as a duplicate. That makes it safe to retry a
report after a network error. If two genuinely different operations would look
identical, give them an explicit key. See [Idempotency](/core-concepts/idempotency).

Use [sub-steps](/core-concepts/sub-steps) to record the parts of a larger
