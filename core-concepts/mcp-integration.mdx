---
title: MCP
description: Let an AI assistant investigate threads, violations and entity profiles on your Engine.
---

Your Engine has a built-in MCP server. Connect an assistant such as Claude,
Cursor or your own agent to ask questions like "why did this refund fail?" or
"which customers had approval violations this week?"

## Connect

| Setting | Value |
| --- | --- |
| Transport | Streamable HTTP |
| URL | `https://threadify.example.com/mcp` |
| Header | `X-API-Key: YOUR_ENGINE_API_KEY` |

Use your Engine's address from **Settings → Engine**. The assistant sees what
the API key can see, so for a shared assistant use a
[service account](/authentication#create-an-api-key) with read-only access.

## Tools

| Tool | What it does |
| --- | --- |
| `search_threads` | Find threads by contract, actor, status, tags or date |
| `get_thread` | Fetch one thread's steps, history, actors and validation results |
| `get_contract_violations` | List violations across threads, by contract, reference or severity |
| `get_entity_profile` | Fetch an entity's profile, metrics and health |
| `query` | Run any [GraphQL](/api-reference/overview) query, for anything the other tools don't cover |

The `graphql://schema` resource gives the assistant the full schema. Three
prompts are included: `investigate_thread`, `analyse_entity_delivery` and
`identify_delivery_failures`. Your MCP client shows each tool's inputs.

## If it finds nothing

Check that the URL points to the Engine that receives your data, that the key
can read threads, and that the assistant isn't filtering by the wrong contract,
status or dates. Very recent activity can take a few seconds to appear.

## Investigating vs. enforcing

MCP lets an assistant read history. It doesn't stop anything. If an agent's own
tool should only run when a contract allows it, call
[`waitFor`](/core-concepts/execution-waits) inside that tool.
