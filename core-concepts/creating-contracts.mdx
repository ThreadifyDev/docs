---
title: Write a contract
description: Describe the steps a run must follow, who may perform them, and what data they need.
---

A contract is a short text file that says which steps a thread may record, in
what order, by which role, and with what data. You write it in a Gherkin-style
language. Threadify compiles it into fixed rules; nothing is interpreted by AI
when a run is checked.

Keep each contract to one focused part of a process, such as refund approval,
rather than the whole business.

## Example

Save this as `refund.feature`:

```gherkin
Feature: refund_review
Version: 1
Description: Approve and record a valid refund.

Step: "approval"
  Description: "The processor approved the refund request."
  Required context: "reference" means "Original payment reference."

Step: "refund"
  Description: "The processor recorded the completed refund."
  Required context: "reference" means "Original payment reference."
  Required context: "amount" means "Amount refunded."
  Required context: "currency" means "Currency of the refund."
  Required context: "receipt" means "Refund receipt identifier."
  Optional context: "note" means "Additional refund explanation."

Rule: Approve the request
  When step "approval" is submitted
  Then owner must be "processor"
  And this step is an entry point
  And content "reference" must not be empty

Rule: Record the refund
  When step "refund" is submitted
  Then owner must be "processor"
  And step "approval" must have succeeded
  And content "reference" must equal approval.reference
  And content "amount" must be a number greater than 0
  And content "currency" must be one of "GBP", "USD", "EUR"
  And content "receipt" must match regex "^RF-[0-9]{8}$"
  And this step is terminal
```

What each part does:

- **`Feature`** is the contract's name. Threads refer to it as `refund_review`
  (or `refund_review:1` for a specific version).
- **`Step`** blocks describe what a step means and which context fields it
  carries. `Required context` must be sent with the step; `Optional context` may
  be left out. Anything after `means` is a plain-language description of the
  field.
- **`Rule`** blocks hold the checks for one step. Every clause in a rule must
  hold. Each step needs exactly one rule.

This contract says: a run starts with `approval`, which needs a reference.
`refund` can only happen after a successful approval, must use the same
reference, and must carry a positive amount, a supported currency and a
well-formed receipt. A valid `refund` completes the thread.

Only the sentences listed in the [rule reference](/core-concepts/contract-rules)
are accepted. Anything else is an error, so a typo can't silently weaken a rule.

## Preview and publish

In the dashboard, open **Contracts** and paste the source into the editor. Or use
the CLI:

```sh
threadify-cli contracts preview --file refund.feature
threadify-cli contracts create --file refund.feature
```

`preview` checks the contract and shows how it compiled, without saving it.

## Update a contract

Raise `Version`, edit the rules, and publish again:

```sh
threadify-cli contracts update --id CONTRACT_ID --file refund.feature
```

Each version is kept. Threads that are already running stay on the version they
started with.

## Steps that run in parallel

If two steps can run at the same time, list them in a `Group` after the rules:

```gherkin
Group: "parallel_reviews"
  Given parallel steps are "fraud_review", "stock_review"
  And all parallel steps must succeed
  And combined duration must be within "5m"
```

Each member still needs its own `Rule`. If a later step needs both reviews to
have finished, say so in that step's rule:

```gherkin
  And step "fraud_review" must have succeeded
  And step "stock_review" must have succeeded
```

## When checks happen

Checks on a step's **content** and **owner** happen when the step is submitted.
If they fail, the step is rejected and not recorded.

Checks on **order, prerequisites, retries and timing** happen just after the
step is recorded. If one fails, the step stays recorded and is marked as a
violation. To wait for that result, or to ask for permission before acting, use
[execution waits](/core-concepts/execution-waits).
