---
title: Roles and access
description: Engine roles, thread access levels and contract roles, and how they differ.
---

Three separate settings control who can do what:

| Setting | Controls | Set by |
| --- | --- | --- |
| Engine role: `admin`, `member`, `viewer` | What a person can do in the dashboard and management APIs | Inviting someone from **Team** |
| Thread access level | What a service can do on one thread, and which notifications it receives | Creating, joining or [being invited to](/core-concepts/thread-collaboration/inviting-parties) a thread |
| Contract role, such as `processor` | Which party may report each step | The `owner must be` clauses in a [contract](/core-concepts/creating-contracts) |

## Engine roles

| Role | Can |
| --- | --- |
| `admin` | Everything below, plus invite and remove members and delete contracts |
| `member` | Create and edit contracts, entity profile types, API keys and service accounts, and run queries |
| `viewer` | Read contracts, profile types and members, and run read-only queries |

## Thread access levels

| Level | Can | Notifications |
| --- | --- | --- |
| Owner | Read, write, invite others, close the thread | All |
| Participant | Read, write, close the thread | Outcomes and validation results for its own steps |
| Observer | Read only | Critical, timeout and retry-limit violations |
| External | Read its own data, write | Outcomes of its own steps |

The service that creates a thread is its owner. A service that
[joins by ID](/core-concepts/thread-collaboration/joining-threads) is a
participant. A party that joins with an invitation gets the level the invitation
granted.

The access level and the contract role are independent: a participant with the
`processor` role can report `processor` steps; the same participant with a
different role can't.

For users and API keys, see [Authentication](/authentication).
