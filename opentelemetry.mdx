title: OpenTelemetry

If your services are already instrumented with OpenTelemetry, you don't need to
call the SDK for every step. Each span becomes a step, and spans from the same
run become one thread.

Report each operation once: either as a span or as an SDK step, not both.

## Send spans to your Engine

Point any OTLP exporter at your Engine with an Engine API key:

```sh
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT='https://threadify.example.com/v1/traces'
export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL='http/protobuf'
export OTEL_EXPORTER_OTLP_TRACES_HEADERS="X-API-Key=$THREADIFY_API_KEY"
```

If your exporter doesn't read these variables, set the same values in its options.

| | |
| --- | --- |
| Endpoint | `POST /v1/traces` |
| Format | OTLP over HTTP, protobuf (`Content-Type: application/x-protobuf`) |
| Authentication | `X-API-Key` header with an Engine API key |
| Compression | gzip, optional |
| Limits per request | 64 MiB and 10,000 spans |

JSON and gRPC aren't accepted. If your exporter only speaks gRPC, run an
OpenTelemetry Collector that receives gRPC and exports OTLP/HTTP to Threadify.

## Or use the SDK exporter

The SDKs include a span exporter that sends spans over your existing Threadify
connection, so you don't need a separate endpoint or key.

<CodeGroup>
```javascript JavaScript
import { Threadify } from '@threadify/sdk';
import { trace } from '@opentelemetry/api';
import { BasicTracerProvider, BatchSpanProcessor } from '@opentelemetry/sdk-trace-base';

const connection = await Threadify.connect(process.env.THREADIFY_API_KEY, 'payment-service', {
  engineUrl: 'https://threadify.example.com',
});

const exporter = connection.createSpanExporter({
  // span attribute → Threadify reference
  refs: { 'customer.id': 'customer_id' },
});

const provider = new BasicTracerProvider({
  spanProcessors: [new BatchSpanProcessor(exporter)],
});
trace.setGlobalTracerProvider(provider);
```
```go Go
import threadifyotel "github.com/ThreadifyDev/go-sdk/otel"

exporter := threadifyotel.NewSpanExporter(conn, threadifyotel.SpanExporterOptions{
    // span attribute → Threadify reference
    RefsMap: map[string]string{"customer.id": "customer_id"},
})
```
```python Python
# pip install 'threadify-sdk[otel]'
exporter = connection.create_span_exporter(options={
    # span attribute → Threadify reference
    "refs": {"customer.id": "customer_id"},
})
```
</CodeGroup>

`refs` copies span attributes onto the thread as
[references](/core-concepts/external-references). If the attribute already has
the name you want, pass a list instead: `refs: ['customer_id']` (`Refs` in Go).

When your process exits, flush and shut down the tracer provider before you
close the Threadify connection, or the last batch is lost.

## Attributes Threadify reads

| Attribute | Use |
| --- | --- |
| `threadify.thread_key` | Your key for the run. Spans with the same key join the same thread. |
| `threadify.contract` | Contract to follow, as `name` or `name:version` |
| `threadify.step_name` | Step name to use when the span name doesn't match your contract |
| `threadify.label` | Human-readable thread label |
| `threadify.role` | Contract role reporting the step |
| `threadify.ref.<key>` | Adds a reference, for example `threadify.ref.customer_id` |
| `threadify.context.<key>` | Adds step context, for example `threadify.context.amount` |
| `threadify.invocation_id` | Links the span to a [permission grant](/core-concepts/execution-waits#with-opentelemetry) |
| `threadify.run.complete` | Set to `true` on the span that finishes the run |

```javascript
span.setAttribute('threadify.thread_key', 'refund:RF-123');
span.setAttribute('threadify.contract', 'refund_review');
span.setAttribute('threadify.step_name', 'refund');
span.setAttribute('threadify.ref.customer_id', 'CUST-001');
span.setAttribute('threadify.context.amount', 42);
```

## How spans map to threads

| OpenTelemetry | Threadify |
| --- | --- |
| A run (see below) | A thread |
| A span | A step, named after the span unless `threadify.step_name` is set |
| A span event | A [sub-step](/core-concepts/sub-steps) |
| Status `OK`, or `UNSET` with no recorded error | `success` |
| Status `ERROR` | `failed` |

The span status is the step's outcome. Whether the step followed the contract is
checked separately; see
[Recording is not the same as passing](/core-concepts/overview#recording-is-not-the-same-as-passing).

## Choose the thread identity

Threadify decides which thread a span belongs to by looking for these, in order:

1. `threadify.thread_id`: the ID of an existing thread.
2. `threadify.thread_key`: your own key for the run.
3. `workflow.run_id`.
4. The span's trace ID.

So by default, each trace is a thread, unless its spans carry a thread key or
a workflow run ID. Set the same key on every span in one run, and a new key for
each run. Keys follow the same [rules as SDK thread keys](/core-concepts/threads#thread-key-rules),
and the same key resumes the same thread whether you use spans or the SDK.

To follow a contract, start the thread with its contract first, either with
`threadify.contract` on the first span or by calling
[`connection.thread(key, { contract })`](/core-concepts/threads#contracted-sessions).
Later spans can leave `threadify.contract` out. A span that names a different
contract is rejected.

Threads that were created separately are never merged later.

### Ignore workflow.run_id

If you want one thread per trace even when spans carry `workflow.run_id`, turn
that step off:

<CodeGroup>
```text Endpoint
https://threadify.example.com/v1/traces?use_workflow_run_id=false
```
```javascript JavaScript
const exporter = connection.createSpanExporter({ useWorkflowRunId: false });
```
```go Go
useWorkflowRunID := false
exporter := threadifyotel.NewSpanExporter(conn, threadifyotel.SpanExporterOptions{
    UseWorkflowRunID: &useWorkflowRunID,
})
```
```python Python
exporter = connection.create_span_exporter(options={"useWorkflowRunId": False})
```
</CodeGroup>

`threadify.thread_id` and `threadify.thread_key` still apply.

## Finishing a run

When several traces make up one run, the end of one root span doesn't finish
the thread. Set `threadify.run.complete: true` on the span that ends the run. A
thread with a contract finishes when its terminal step passes instead.

Once a thread has finished it rejects further spans, including late ones, so
don't mark a run complete until all its spans have been exported.

## Drop spans you don't need

### In the SDK exporter

<CodeGroup>
```javascript JavaScript
const exporter = connection.createSpanExporter({
  filters: ['healthcheck', 'internal.*'],
});
```
```go Go
exporter := threadifyotel.NewSpanExporter(conn, threadifyotel.SpanExporterOptions{
    Filters: []string{"healthcheck", "internal.*"},
})
```
```python Python
exporter = connection.create_span_exporter(options={
    "filters": ["healthcheck", "internal.*"],
})
```
</CodeGroup>

- `healthcheck` drops spans with exactly that name.
- `internal.*` drops spans whose name starts with `internal.`. A trailing `*` is
  the only wildcard; these aren't regular expressions.
- Matching is case-sensitive and uses the original span name.
- Each span is checked on its own. Dropping a parent doesn't drop its children.

Don't drop spans your contract needs, or the span that completes the run.

### At the Engine

To filter spans from every exporter that posts to `/v1/traces`, open
**Settings → Trace ingestion**, enter one name or `prefix*` per line, preview
against sample span names, and save. Only admins can save rules. With no rules,
every span is kept.

These rules apply only to `/v1/traces`. They don't affect SDK steps or the SDK
exporter.

From the CLI:

```sh
threadify-cli ingestion-rules get > rules.json
# Edit the filters. Keep the "revision" field as it is.
threadify-cli ingestion-rules set --file rules.json
```

To try rules without saving them, write a `preview.yaml`:

```yaml
filters: [healthcheck, "internal.*"]
span_names: [healthcheck, internal.cache, refund]
```

```sh
threadify-cli ingestion-rules preview --file preview.yaml
```

What to expect:

- New rules apply from the next request. History that's already stored doesn't
  change.
- If someone else saved rules after you loaded them, your save fails with `409`.
  Load them again and reapply your change.
- A request whose spans are all dropped still succeeds. The
  `X-Threadify-Filtered-Spans` response header says how many were dropped.
- The settings page shows how many spans were checked and dropped. Retries are
  counted again, so treat these numbers as a guide.
- Dropped spans still count toward your [input bandwidth](/plans-and-limits).

### Remove sensitive fields

Filters drop whole spans. They don't remove attributes, events or messages from
the spans you keep, and Threadify doesn't redact fields for you. Leave sensitive
values out of your instrumentation, or remove them in your Collector before
they're exported.

## Recording vs. stopping

Exported spans arrive after the operation has already run, so they can flag a
problem but can't prevent it. To stop an agent's tool call or a backend action
the contract doesn't allow,
[get permission with the SDK first](/core-concepts/execution-waits), then let the
span report the outcome.
